# Hylo authentication and integration investigation

**Status:** Research, 2026-10-26. The project owner prefers self-hosted Hylo as the platform's foundation. A self-hosted development pilot now runs on a desk-side Docker host; no hosted Hylo account, partner API credential, production integration, or production deployment was tested. No partner participation is implied.

## Findings from upstream

- Hylo's [partner API guide](https://hylozoic.gitbook.io/hylo/guides/api-documentation) describes OAuth 2.0 and OpenID Connect. It says partner credentials are issued manually after contacting Hylo and registering redirect URLs. Verify the current access process and availability directly with Hylo before relying on it.
- The guide describes authorization-code flow for applications acting on behalf of a user, an `openid` scope and ID token, and PKCE with S256. It describes optional `offline_access` refresh tokens. The guide also describes a more limited client-credentials flow for machine-to-machine access. It does not establish that any particular calendar mutation or third-party app will work with either flow in our account.
- The documented hosted endpoints are `https://hylo.com/noo/oauth/auth`, `https://hylo.com/noo/oauth/token`, and `https://hylo.com/noo/graphql`. These are documentation claims, not endpoints we have tested with credentials; the OIDC discovery URL, issuer, JWKS, logout, token lifetimes and deployed behavior still need verification.
- The inspected [Hylo OpenID Connect implementation](https://github.com/Hylozoic/hylo/blob/397372db90683e3e4402fdad9ff37a67712c5c5b/apps/backend/api/services/OpenIDConnect.js) configures PKCE by default, user scopes and client credentials. Its resource-server configuration grants `api:write` only to specially privileged clients. It also sets production cookie domains to `.hylo.com`, while development uses `localhost`. The same source permits all origins in its OIDC client CORS callback. These are source observations for that revision, not a claim about every running deployment. A custom-domain self-host needs configuration/code review and end-to-end testing rather than assuming it works unchanged.
- The inspected [GraphQL schema](https://github.com/Hylozoic/hylo/blob/397372db90683e3e4402fdad9ff37a67712c5c5b/apps/backend/api/graphql/schema.graphql) defines `me`, group and membership queries, group-role fields, and create/update/delete post mutations. `PostInput` contains event times, group IDs and a public-visibility flag. A schema lists capabilities, not a guarantee of partner API permission, publication authority, webhook support, or compatibility with our approval workflow.
- Hylo's documented [group embed](https://hylozoic.gitbook.io/hylo/guides/creating-an-iframe) is a possible presentation experiment. Verify branding, accessibility, public visibility, browser cookie behavior and actual permissions before adopting it.

## Proposed integration boundary

Use Hylo as the community and organizer identity foundation **if** the local self-hosted pilot verifies this is supported. Public calendar browsing and basic volunteer participation remain account-free. An organizer-facing calendar service can use Hylo as an OIDC provider via a server-side authorization-code flow with PKCE, a per-attempt `state` and `nonce`, exact redirect matching, validated issuer/audience/signature/expiry and secure local sessions. Request only necessary scopes; don't request refresh tokens until needed and approved. Never ask for Hylo passwords or reuse browser cookies.

Authentication identifies a person; it does not prove authority to publish for a particular organization. Map Hylo's stable identity and group identifiers to a separately verified organization and its approved roles. Check current group membership and required rights on each privileged action, handle revocation and loss of access, deny by default, and keep draft/image/volunteer data private. A Hylo group role should grant calendar authority only after the operator and organization explicitly authorize that mapping. Treat private groups, membership lists and drafts as private; avoid logging tokens, student data or personal volunteer records.

The community calendar retains its own source attribution, drafts, review state and approved public catalogue until a real integration establishes another source of truth. Hylo remains the source of truth for its own user accounts, memberships and community content. Use supported APIs for synchronization rather than directly accessing Hylo tables or assuming all apps can share Hylo's internal database. Publication or cross-posting into Hylo must be an explicit separately authorized action, with tested visibility, update/cancel behavior and reconciliation. No Facebook integration is assumed.

## Validation plan

1. Inspect and run a local self-hosted Hylo instance with test data; determine its container, database, environment, identity-client provisioning and licensing requirements. Validate custom-domain cookies, OIDC discovery, issuer, scopes, PKCE, token rotation, logout and account deletion. If upstream guidance or hosted partner access is needed, ask the owner before contacting Hylo.
2. With test identities and two independently controlled test groups, demonstrate OIDC login to a local calendar service; verify signature, issuer, audience, state/nonce, expiry, secure cookies, logout and revoked access. Do not require sign-in for public browsing.
3. Verify group membership and steward/role data is available to that client. Test organization A cannot access B's drafts or submissions, including after removal from a group; document how role changes propagate and what happens when Hylo is unavailable.
4. Test one synthetic event's read, creation, explicit approval, visibility, update and cancellation via the supported API with consent and test groups. Determine whether events should live in Hylo, the calendar, or be synchronized, and test duplicate and failure recovery. Do not publish a real event as a test.
5. Evaluate self-hosted Hylo branding and custom-domain configuration, certificates, backups and supported integration with OpenSignup. Do not assume a custom domain or a single shared database already works.

## Decisions still open

Self-hosted operational readiness, API client provisioning and terms, cross-subdomain identity and session design, organization-to-group mapping and verification, exact public/private content model, data ownership, third-party authentication support, brand/custom-domain capability, operator, and deployment/retention policy. The public calendar needs no registration regardless of organizer identity choice.

## Local pilot checkpoint

An isolated self-hosted pilot was started from upstream revision `c141ceec71dae2db9f84c36ccae6bab5fd37e943`. The web login page rendered; the GraphQL API responded; OIDC discovery and JWKS returned localhost URLs after a pilot-only Vite proxy adjustment. A synthetic password login, incorrect-password rejection, session identity and logout succeeded. A second synthetic user was denied an edit to the first user's private group. A Postgres dump restored into a separate pilot database with matching synthetic user and group counts. These checks do not prove cross-app OIDC sign-in, complete organization isolation or backup recovery for production.

Setup required a Node 24 container build instead of the obsolete upstream web Dockerfile, PostGIS 18 for the upstream schema dump, a pilot-only workaround for the starter seed's nonexistent `groups_posts.active` field, explicit configuration to disable Segment analytics, and invalid placeholder keys for external integrations required by startup. The upstream seed marks migrations as applied, which must not be mistaken for proof that every migration was validated. The environment has no production data, no public exposure, and no live payment, external login or email configuration. See `infra/hylo-pilot/README.md` for the reproducible setup, remaining checks and retained pilot volumes.
